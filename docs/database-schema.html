How to read it

Five rules explain why the tables look the way they do. Without them the list below is just nouns. They are numbered because the rest of the documentation refers to them by number.

  1. Almost every table carries school_id

    The product is sold to separate, independent schools; a tenant is a customer, not a branch. The column is declared on TenantBase so a new table cannot quietly be created without one, and a missing tenant key is a data leak between customers. Three tables derive from TimestampedBase instead and carry none: schools is the tenant, and permissions and scheduled_jobs belong to the software rather than to any one school.

  2. Year-scoped facts hang off enrolment_id

    A fee, an attendance mark, a bus seat and a set of marks all belong to a child's year in a class, so they point at enrolments. A name and a date of birth belong to the child for life, so they point at students. Backwards, and last year's data follows a child into the new class.

  3. Money is never edited

    An invoice is voided and reissued; a payment is reversed by a contra entry — a second row with a negative amount and reverses_payment_id pointing at the original. Nothing is rewritten in place, so the history stays reconstructable.

  4. A balance is always a SUM

    Payments allocate to invoice lines through payment_allocations, oldest first. What a family owes is computed from those rows every time it is asked for, never read from a stored column.

  5. Destructive actions carry a reason

    void, status_change and delete refuse to commit without one, and what is stored is the words the person typed — never a string the software made up.

Empty does not mean unfinished. Each of the 25 empty tables belongs to a feature that is built and has working endpoints — admission has taken no applications, payroll has run no cycle, nobody has requested leave. The schema is real; only the rows are missing.

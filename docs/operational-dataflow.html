4. Detailed Operational Workflows: System, Master Data & Academics

Granular data flows for authentication, tenant scoping, student master, admissions, academics, and attendance.

Workflow 1.1: User Authentication, Credential Verification & JWT Issuance Operational Flow
A. Workflow Overview
Real-Life Context: A school administrator, teacher, or receptionist logs in to access their operational workspace.
Primary Actor: Any valid system user (Admin, Principal, Teacher, Accountant, Receptionist, Parent).
Triggering Event: User submits email/username and password at /login or the mobile login screen.
Business Problem: Securely authenticating user identity without exposing plaintext passwords and generating time-bound access claims.
Expected Outcome: A cryptographically signed JWT bearer token containing user ID, school ID, active roles, and granular permissions.
B. Step-by-Step Processing Pipeline
  1. User Action: The user enters email and password into the login form and clicks 'Sign In'.
  2. Frontend Processing: LoginPage.tsx packages credentials into a JSON POST payload and dispatches to POST /api/v1/auth/token.
  3. Backend Validation: FastAPI receives request; validates fields against LoginRequest schema. Queries users table by email.
  4. Credential Verification: Passes entered password and users.hashed_password to Bcrypt/Passlib. Aborts with HTTP 401 if invalid.
  5. Role & Permission Resolution: Backend executes joined query across user_roles, roles, and role_permissions to collect all active permission strings.
  6. Token Generation: Encodes user claims (sub=user.id, school_id, roles, permissions, exp) into a signed JWT.
  7. Final Output: Token returned in HTTP response; stored in browser localStorage / SecureStore; user redirected to /dashboard.

Workflow 1.2: Multi-Tenant School Isolation & Database Scoping Operational Flow
A. Workflow Overview
Real-Life Context: Ensuring that data from Sunrise Public School is strictly inaccessible to any other school operating on the platform.
Primary Actor: Every authenticated user and automated background process.
Triggering Event: Every incoming API request intercepted by dependency injection.
Business Problem: Preventing accidental data leakage between independent schools sharing a single PostgreSQL database instance.
Expected Outcome: Every database query automatically appends WHERE school_id = :school_id.
B. Step-by-Step Processing Pipeline
  1. User Action: Client application sends an HTTP request with Bearer JWT token in Authorization header.
  2. Frontend Processing: client.ts automatically injects the active token into every outgoing Axios/fetch request.
  3. Backend Dependency Extraction: FastAPI executes get_current_user dependency, validating JWT signature and extracting school_id claim.
  4. Database Session Scoping: All repository queries inherit from TenantBase, which automatically injects school_id into SQLAlchemy queries.
  5. Query Execution: PostgreSQL executes the isolated SQL statement; records with different school_id are invisible at the database engine level.
  6. Final Output: Data returned strictly belongs to the caller's school.
C. Data-Flow Architecture Diagram
[Client Request with JWT Token] │ ▼ [FastAPI Dependency: get_current_user] │ ▼ (Extracts validated school_id from token claims) [SQLAlchemy Query Builder (TenantBase)] │ ▼ [READ] / [INSERT] / [UPDATE] [PostgreSQL Table: ANY TENANT TABLE] ──► Automatically filtered: WHERE school_id = :tenant_id │ ▼ [Tenant-Isolated Result Set]

Workflow 1.5: User Access Role Assignment, Custom Roles & Token Invalidation Operational Flow
A. Workflow Overview
Real-Life Context: School Administrator assigns or revokes operational roles (such as Librarian, Teacher, or Accountant) to staff accounts via the User Access console.
Primary Actor: System Administrator or School Principal.
Triggering Event: Admin updates role assignments for a staff member at /user-access and clicks 'Save Roles'.
Business Problem: Enforcing granular role-based access control (RBAC), preventing privilege escalation, and ensuring permission changes take immediate effect across sessions.
Expected Outcome: User-role bindings synchronized in user_roles; users.token_version incremented to invalidate stale JWTs; compliance logged in audit_log.
B. Step-by-Step Processing Pipeline
  1. User Action: Admin opens /user-access, selects a staff user (e.g. librarian@sunrisepublic.edu), toggles role assignments (e.g. checks 'Librarian'), and saves.
  2. Frontend Processing: UserAccess.tsx validates selections and dispatches PUT /api/v1/auth/users/{user_id}/roles with payload {'role_names': ['Librarian']}.
  3. Backend Authorization: FastAPI verifies caller holds auth.user.manage permission and both caller and target user share the same school_id.
  4. Role Resolution: Resolves role IDs from roles table matching school scope; validates role exists.
  5. Junction Sync: Executes atomic delete/insert on user_roles table binding the user to the updated role set.
  6. Security Invalidation: Increments users.token_version (+1) to force re-authentication or claim refresh on subsequent API calls.
  7. Audit Log: Writes compliance record to audit_log recording admin ID, target user ID, timestamp, and new role assignments.

Workflow 2.1: Permanent Student Master Identity Creation & Admission Number Allocation Operational Flow
A. Workflow Overview
Real-Life Context: A newly admitted student is officially enrolled into the school's permanent records registry.
Primary Actor: School Registrar or Admission Officer.
Triggering Event: Admissions conversion execution or direct student registration.
Business Problem: Establishing an unchangeable lifetime record for a student that persists across all future years and class promotions.
Expected Outcome: Permanent records created in users and students with a unique, unalterable admission_no.
B. Step-by-Step Processing Pipeline

  5. Student Record Insertion: Inserts child row into students table referencing users.id.
  6. Family Relationship Linkage: Links the student to guardian records via student_guardian table.
  7. Final Output: Permanent student record established; returns student master ID and profile data.

6.2 Conceptual Distinction vs. Actual System Architecture

In general academic database theory:

  • Student ID conceptually represents the student as a physical individual and permanent institutional entity.
  • Enrollment ID conceptually represents a registration event or academic contract between the student and a school programme for a particular academic year or semester.
Mandatory Engineering Clarification:
“The current implementation does not maintain a distinct string business identifier called ‘Enrollment ID’. 6.4 Multi-Year Practical Lifecycle Simulation

To demonstrate how the system prevents data corruption across academic transitions, consider the realistic scenario of student Aarav Sharma:

Case Study: 3-Year Academic Lifecycle (Class 5-A to Class 7-A)

Year 1 (Academic Year 2024-25 — Admission):
• Aarav joins Class 5-A on 10 April 2024.
• System creates permanent record: students.id = 12, admission_no = 'ADM-2024-001', linked to users.id = 45.
• System creates first session enrollment: enrolments.id = 42 with academic_year_id = 1 (2024-25), class_section_id = 5 (5-A), roll_no = 12, status = 'active'.
• 180 daily attendance marks in attendance link to enrolment_id = 42.
• 12 monthly fee invoices in fee_invoices link to enrolment_id = 42.

Year 2 (Academic Year 2025-26 — First Promotion):
• In March 2025, the Principal runs Session Rollover from 2024-25 to 2025-26.
• System updates existing enrollment enrolments.id = 42: sets status = 'promoted' and left_on = '2025-03-31'.
• System inserts new enrollment: enrolments.id = 95 with academic_year_id = 2 (2025-26), class_section_id = 8 (6-A), roll_no = 14, status = 'active'.
• Crucial Invariant: Aarav's students.id = 12 and admission_no = 'ADM-2024-001' remain completely unchanged.
• New Year 2 attendance records and fee invoices point to enrolment_id = 95. Past Year 1 attendance records still point safely to enrolment_id = 42!

Year 3 (Academic Year 2026-27 — Second Promotion):
• In March 2026, Session Rollover advances Aarav to Class 7-A.
• System updates enrolments.id = 95: sets status = 'promoted'.
• System inserts new enrollment: enrolments.id = 168 with academic_year_id = 3 (2026-27), class_section_id = 11 (7-A), roll_no = 15, status = 'active'.
• Aarav's permanent student ID is still students.id = 12.
Why This Architectural Separation Prevents Critical Bugs:
In legacy educational ERPs where class_section_id was placed directly on students, promoting a student silently overwritten the student's current class. As an unintended side effect, querying past attendance or past report cards would re-parent historical records to the new class! In Sunrise ERP, splitting lifetime facts (students) from year-scoped facts (enrolments) means promotion creates rows instead of destroying them. Past nominal rolls and past fee ledgers can be reconstructed at any time with 100% mathematical fidelity.

8. Consolidated Database Table Reference

Complete technical classification of active database tables supporting operational workflows.

The Sunrise ERP schema organizes relational data across six distinct architectural classifications. Understanding these categories is essential for database administrators, query optimization, and transaction design.

8.1 Architectural Table Classifications
Category Architectural Responsibility Operational Invariants & Examples
Core / Master Tables Stores foundational business entities that exist independently of specific transactions (e.g. users, students, employees, classes, subjects). Rarely deleted; uses soft-deactivation flags (is_active); primary keys widely referenced as foreign keys across the schema.
Transaction Tables Records operational events that occur at specific points in time (e.g. fee payments, attendance marks, exam scores, stock requisitions). High write volume; strictly immutable financial records; financial rows use contra reversals rather than in-place updates.
Linking / Junction Tables Resolves Many-to-Many (M:N) relationships between master or transactional entities (e.g. student_guardian, class_subject_teacher, payment_allocations). Carries composite foreign keys; frequently maintains unique constraints to prevent duplicate associations.
Audit & History Tables Preserves immutable chronological logs of sensitive actions, destructive state changes, and session rollover progression (e.g. audit_log). Append-only; requires mandatory human-typed explanation reasons; never updated or purged.
Configuration Tables Governs school-wide operational rules, feature toggles, grading boundaries, and fee schedules (e.g. settings, grade_bands, fee_plans). Low row counts; modified primarily by administrators during school setup or annual review.
Tenant-Scoped Tables Every table deriving from TenantBase carrying a non-nullable school_id foreign key pointing to schools.id. 102 of 105 tables in Sunrise ERP (72 live with active records, 33 reserved); guarantees complete multi-tenant database isolation.

9.2 Architectural Invariants Verified in Production
1. Multi-Tenant Scoping Invariant:
102 of 105 tables inherit from TenantBase. Foreign key constraints to schools.id are enforced at the database level. Queries without school_id are impossible under standard repository patterns.
2. Financial Immutability & Audit Invariant:
In the fees module, money is never edited or deleted in place. If a payment bounces or is entered in error, the system mandates a contra payment entry with negative amount and reverses_payment_id pointing to the original voucher. Furthermore, destructive actions (e.g. deleting a notice or voiding an invoice) strictly require a human-typed explanation string saved to audit_log.
3. The Lifetime vs. Session Split Invariant:
The database strictly maintains the boundary between students (lifetime identity, admission number) and enrolments (session-scoped class membership, roll number). Promoting a student creates a new row in enrolments and marks the prior row promoted, preserving past attendance, report cards, and fee ledgers without corruption.

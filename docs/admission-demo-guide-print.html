Complete Digital Admission Dossier & Automated Institutional Enrollment

System: Sunrise Public School ERP v2.0
Specification: CBSE & Institutional Standard
Security: §15 Health Gated / Multi-Tenant Scoped

Fundamental Architectural Invariant: Application 360° = Complete Digital Admission Dossier

1. Enquiry Slip → 2. Draft Application → 3. Digital Dossier (10 Tabs) → 4. Verification → 5. Collect Fee → 6. Auto-Enrolled Roster

Core Principle: Application 360° is not merely a read-only applicant summary or assessment console. It is the school's Complete Digital Admission Dossier allowing the Admission Cell to input, review, and persist all 11 CBSE statutory sections. Furthermore, successful application-fee payment serves as the single, atomic trigger for student enrollment: it generates the permanent institutional Admission Number, allocates the balanced section, assigns the roll number, creates student & parent logins, and migrates verified documents in a 100% all-or-nothing database transaction.

Database Model & Serialization Verification Matrix

Verified database models and serialization mapping across backend APIs and frontend dossier components:

Dossier Section Underlying DB Table Authoritative Columns Serialization & API Gating
Student Personal applications first_name, middle_name, last_name, date_of_birth, gender, nationality, religion, caste_category, mother_tongue, aadhaar_last4 Directly serialized on _detail(); aadhaar strictly restricted to last 4 digits.
Preferences applications class_applying_for, stream, second_language, optional_subject, preferred_section, transport_required Preserves optional subjects and section preferences for balance allocator.
Parents & Guardians application_guardians relation, full_name, date_of_birth, qualification, occupation, designation, organisation, annual_income_band, office_address, mobile, email Fully serialized via _guardian_out(); guarantees zero data loss on modal reload.
Siblings & Claims application_siblings student_id, name, age, school_name Links to real students.id; validated by refresh_claims().
Address & History applications address (JSON), previous_school (JSON) Handles both line1 and address_line_1 defensively; TC details stored.
Medical (§15) application_medicals blood_group, known_allergies, chronic_conditions, regular_medication, emergency_doctor, consent_for_emergency_treatment Separately gated by admission.medical.read; receptionist access refused.
Declarations applications declarations (JSON) Stores parent_signature_name, accuracy acceptance, and declaration timestamp.
Enrollment Result students & enrolments students.admission_no, enrolments.class_section_id, enrolments.roll_no Resolved dynamically in _detail() whenever student_id is populated.

Verify Active Enrolments and Section Allocation SELECT e.student_id, s.admission_no, cs.label AS class_section, e.roll_no, e.status FROM enrolments e JOIN students s ON e.student_id = s.id JOIN class_sections cs ON e.class_section_id = cs.id WHERE e.status = 'active'; -- 3.
